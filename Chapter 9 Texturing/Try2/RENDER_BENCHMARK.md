# Цена материальной системы: замеры рендера

Сравниваются две ревизии одного движка:

- **до** — `c5601c9`, последний коммит перед материальной системой (`a1cbb9e` и далее);
- **после** — текущее дерево: материалы как данные, кэш PSO, `SetMaterial`, render state, инстансы.

## Запуск

```powershell
.\tests\RunRenderBenchmark.ps1
```

Скрипт генерирует сцены (`tests/GenerateRenderBenchmarkScenes.ps1`), создаёт worktree ревизии «до» в `tests/.build/render-before`, накладывает на неё тот же замерный патч, собирает обе версии в **Release x64** и проводит серию запусков. `-SkipBuild` повторяет только замеры, `-BuildOnly` только собирает. Параметры: `-Runs` (по умолчанию 5), `-WarmupFrames` (300), `-MeasuredFrames` (1500).

Результаты: `tests/.build/render-benchmark/summary.md` (сводная таблица), `results.csv` (статистика каждого запуска), `<конфигурация>-runN.csv` (каждый кадр).

## Методика

- Release-сборки обеих ревизий, одинаковый компилятор и настройки проекта; в обеих включён `TRACY_ENABLE`, как в обычной Release-сборке движка.
- Режим `--play --no-hot-reload --scene …`: отдельное окно игры без UI редактора, размер окна по умолчанию, vsync выключен в обеих ревизиях.
- Прогрев: отсчёт начинается, когда сцена загружена и очередь ресурсов пуста (`IsSceneLoading`, `HasPendingLoads`); затем 300 кадров не записываются. Если загрузка возобновилась во время прогрева, прогрев начинается заново.
- N = 5 запусков на конфигурацию, по кругу; на чётных кругах порядок обратный, чтобы нагрев и изменения питания ноутбука распределялись поровну.
- В каждом запуске считаются медиана, p95 и p99 по кадрам; в таблице — медиана этих значений по запускам.

Замерный патч (`FrameBenchmark.h`, вызовы в `Application.cpp` и `Try2.cpp`) одинаков в обеих ревизиях; для «до» скрипт вставляет его по точным якорям и падает, если якорь не найден ровно один раз. Метрики:

| Метрика | Что входит |
|---|---|
| `frame_ms` | интервал между началами соседних кадров: всё, включая ожидание GPU и Present |
| `cpu_frame_ms` | от начала кадра до возврата из `EndFrame` (Present) |
| `draw_ms` | `Engine::Draw`: сбор и сортировка подач, `SetMaterial`, запись команд — то, что изменила материальная система |

В Tracy те же участки видны как зоны `Draw`, `Render collect and sort` и `Render submit (bind material + draw)`.

## RenderDoc-захваты до/после

```powershell
.\tests\RunRenderBenchmark.ps1 -BuildOnly
.\tests\CaptureRenderDoc.ps1
```

Нужен установленный RenderDoc (проверено с 1.47). Скрипт запускает обе Release-сборки через `renderdoccmd capture`. Сцена: по умолчанию `MaterialsBaseline.json` и `RenderBenchmark4096.json`; другие можно передать через `-Scenes`. Захват запускает сам движок, а не клавиша: `FrameBenchmark.h` при `LS_RENDERDOC_CAPTURE=1` ждёт загрузки сцены и 120 кадров прогрева, затем вызывает `TriggerCapture()` из in-application API RenderDoc (`Common/ThirdParty/renderdoc/renderdoc_app.h`, MIT). Поэтому в обеих ревизиях захватывается одинаковый по счёту кадр после прогрева. Если процесс запущен без RenderDoc, движок пишет `RENDERDOC_NOT_LOADED` и завершается с кодом 4.

Результат лежит в `tests/.build/renderdoc/<before|after>-<сцена>/`: `capture_frame*.rdc` и `thumbnail.png`. Открывать в `qrenderdoc`. Снятые 2026-11-20 захваты весят 3.5–4.7 МБ.

### GPU-разметка проходов (RenderDoc + Tracy)

`IRenderAdapter::BeginGpuRegion/EndGpuRegion` и RAII-обёртка `GpuRegion` (`Commons.h`) размечают командный список. D3D12-реализация делает два действия: пишет `BeginEvent/EndEvent` (формат PIX, его читают RenderDoc и PIX) и открывает GPU-зону Tracy через контекст `TracyD3D12` очереди `Direct queue` с временными метками на GPU. Регионы:

```
Frame
  Resource uploads
  Clear back buffer
  Scene | Scene (editor viewport: color + entity ID)
    Opaque and masked
    Terrain
    Transparent (back to front)        — только если в кадре есть blend
    Picking readback (entity ID pixel) — только в редакторе при запросе выбора
  Material editor preview              — когда открыт Material Editor
  Editor UI (ImGui)
```

`CaptureRenderDoc.ps1` после каждого захвата открывает его встроенным Python RenderDoc (`tests/RenderDocMarkers.py`) и пишет `markers.txt`: дерево регионов с числом отрисовок в каждом. В захватах 2026-11-20:

| Сцена | Отрисовок «до» | Отрисовок «после» | Регионы «после» |
|---|---:|---:|---|
| MaterialsBaseline | 9 | 9 | Frame → Scene → Opaque and masked: 9 |
| RenderBenchmark4096 | 4097 | 4097 | Frame → Scene → Opaque and masked: 4097 |

Число вызовов совпадает: материальная система не добавила и не потеряла отрисовок, разница во времени — в стоимости каждого вызова. У ревизии «до» разметки нет. Регионы прозрачной очереди, пикинга, превью и ImGui в режиме `--play` не возникают. Их баланс проверяют `RunRenderStateTests.ps1` и `RunMaterialTests.ps1` в редакторе: debug layer D3D12 там без ошибок. Незакрытые регионы `EndFrame` закрывает сам и пишет предупреждение в отладочный вывод.

Таблица замеров выше снята до появления разметки. Контекст Tracy добавляет несколько timestamp-запросов и одно чтение readback-буфера на кадр; при повторном замере эта цена войдёт в «после».

Картинка «до» и «после» различается: новая ревизия считает свет по GGX в линейном пространстве с одним явным sRGB-кодированием на выходе (см. `MATERIALS.md`), старая давала пересвеченные цвета. Это изменение шейдинга вместе с материальной системой, а не ошибка захвата.

## Конфигурации

| Имя | Ревизия | Сцена |
|---|---|---|
| `before-4096-inline` | до | `RenderBenchmark4096.json`: 4096 кубов, 64 варианта материала (цвет, roughness, у части albedo/normal) в старом формате |
| `after-4096-inline` | после | та же сцена |
| `after-4096-instances` | после | `RenderBenchmark4096Instances.json`: тот же вид, материалы — 64 инстанса одной базы через `materialComponent` |
| `before-baseline` | до | `MaterialsBaseline.json`, маленькая демо-сцена старого формата |
| `after-baseline` | после | та же сцена |

Обе 4096-сцены используют только поля старого формата (у инлайн-варианта), поэтому одна и та же сцена читается обеими ревизиями. Генератор детерминирован.

## Что учитывать при чтении

- «После» рисует другим шейдером: GGX, ORM, emissive, sRGB-путь. Разница кадра включает цену нового шейдинга, а не только архитектуры биндинга; архитектурную часть изолирует `draw_ms`.
- Отсечения по frustum нет ни в одной ревизии: рисуются все 4096 объектов.
- Ноутбук с двумя GPU (Intel + NVIDIA): адаптер выбирается по умолчанию и одинаков для обеих ревизий, но зависит от настроек питания и драйвера. Замер стоит делать от сети.
- Файлы прогреты, кэши ОС не очищались.

## Результаты — 2026-11-20

Intel Core 7 240H, NVIDIA GeForce RTX 5070 Laptop GPU + Intel Graphics (адаптер по умолчанию), Windows 11, окно 800×600, Release x64, MSVC 14.52. 5 запусков на конфигурацию, 300 кадров прогрева и 1500 измеряемых в каждом. Миллисекунды; медиана по запускам от статистик каждого запуска.

| Конфигурация | Кадр медиана | Кадр p95 | Кадр p99 | CPU draw медиана | CPU draw p95 | CPU draw p99 |
|---|---:|---:|---:|---:|---:|---:|
| before-4096-inline | 1.906 | 2.340 | 2.581 | 1.788 | 1.983 | 2.262 |
| after-4096-inline | 3.760 | 4.050 | 4.285 | 3.624 | 3.846 | 4.101 |
| after-4096-instances | 3.752 | 4.052 | 4.370 | 3.612 | 3.839 | 4.158 |
| before-baseline | 1.109 | 1.876 | 2.408 | 0.009 | 0.027 | 0.052 |
| after-baseline | 1.034 | 1.671 | 2.425 | 0.017 | 0.054 | 0.091 |

CPU-время кадра до возврата из Present совпадает с временем кадра с точностью до 0.002 мс, поэтому в таблицу не вынесено (есть в `summary.md`).

**Цена материальной системы — около 1.8 мс CPU на кадр при 4096 отрисовках**, то есть примерно 0.45 мкс на одну отрисовку: `Engine::Draw` 1.79 → 3.62 мс (×2.0), кадр 1.91 → 3.76 мс. Сцена ограничена процессором: почти весь кадр — это запись команд, и рост времени кадра равен росту `draw_ms`. На маленькой демо-сцене (9 мешей) разница в пределах шума: кадр 1.11 → 1.03 мс, `draw` 0.009 → 0.017 мс.

**Инстансы бесплатны в кадре**: 64 инстанса одной базы против 4096 инлайн-материалов дают одинаковые 3.61–3.62 мс. Путь отрисовки одинаков, а PSO общий. Выигрыш инстансов — в данных и редактировании, а не в скорости кадра.

Откуда берётся цена (по коду; доли по отдельности не измерялись). Обе ревизии на каждую отрисовку ставят descriptor heap, PSO, root signature, CBV объекта и материала и копируют константы материала; старая искала PSO по строке в `std::map`. Новая сверх этого:
- собирает `SurfacePipelineKey` для каждой отрисовки: копирует имена entry points, нормализует путь шейдера через `std::filesystem::path::lexically_normal()` (аллокации и разбор пути) и хэширует ключ со строками для поиска в кэше PSO — вероятно, самая дорогая часть;
- ставит ещё две таблицы SRV (ORM, emissive) и CBV прохода;
- до отрисовки собирает и сортирует список подач (`Render collect and sort`), чтобы прозрачное шло после непрозрачного.

Разделить эти доли можно Tracy-захватом зон `Render collect and sort` и `Render submit (bind material + draw)`. Очевидные следующие шаги: хранить найденный PSO в материале вместо ключа на каждую отрисовку, пропускать неизменившееся состояние и сортировать непрозрачные подачи по PSO/материалу. В эту работу они не входят.

Воспроизводимость: первая серия дала те же медианы в пределах 2%. В ней один запуск `after-4096-inline` целиком шёл в ~5 раз медленнее (18.8 мс; вероятно, окно потеряло фокус или процесс попал на энергоэффективные ядра). Медиана по пяти запускам его отбросила, но для чистоты серия повторена; таблица выше — вторая серия, без выбросов (разброс медиан между запусками ≤ 0.13 мс).
