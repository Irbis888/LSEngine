# Resource loading measurements, 2026-10-09

Сравнение со сборкой непосредственно перед этими правками. До изменения файлов сохранены
`tests/.build/loading-baseline/TextureLoadingTests.exe` и обычный Debug `Try2.exe`.
Git для сохранения или сравнения не использовался. Историческая синхронная версия в этот замер не входит.

## Условия

- Одна сцена `Scenes/TextureStreaming1000.json`: 1000 кубов, 1000 отдельных DDS 64×64 RGBA8.
- Debug: `/MDd /Od /Zi /D_DEBUG`, D3D12 debug layer, четыре enkiTS worker threads.
- Настоящие Engine, SceneSerializer, ResourceManager, JobSystem, RenderSystem и D3DRenderAdapter.
  Harness подменяет только две политики редактора: захват ввода и включение физики.
- Одинаковое скрытое D3D12-окно 64×64, две frame resources, `Present(0, 0)`.
- ImGui-интерфейс редактора не рисуется; замер включает реальные Update/Draw движка.
- Начальное состояние каждого процесса: маленькая сцена с одним кубом; затем одинаковый запрос открытия stress-сцены.
- Перед каждым процессом явно прочитаны тот же JSON и все stress DDS; файловый кэш прогрет.
  Холодный диск не измерялся. Процессы запускаются последовательно, без параллельной компиляции.
- Машина: Intel Core i5-12500H, 16 логических потоков; D3D12 использует системный default adapter.
- Три запуска каждого варианта. Лимит pending CPU data у новой реализации — 64 MiB;
  лимит GPU bytes — 64 MiB; публикация сцены — 4 ms. Начальный запуск поддерживает отдельный бюджет 8 ms.

Полная готовность измеряется от принятия запроса открытия сцены до выполнения GPU fence кадра,
в котором записаны uploads всех 1000 текстур. Проверка также требует 1000 созданных объектов.
Это не только быстрый возврат из `LoadScene()` и не только состояние `ResourceState::Ready`.
Самый долгий кадр измеряется от `BeginFrame()` до окончания `EndFrame()`, включая Update/Draw/Present;
пауза тестового цикла между кадрами в него не входит. Между кадрами у обеих сборок одинаковый `sleep_for(1ms)`.

## Результаты

| Вариант | Полная готовность, медиана | Диапазон полной готовности | Самый долгий кадр за 3 запуска |
|---|---:|---:|---:|
| До правок: 4 textures / 4 meshes, GPU 2 ms, scene 32 entities / 2 ms | 8.336 s | 8.272–8.397 s | 63.176 ms |
| Непрерывные consumers, общий кэш geometry, GPU 4 ms | 2.107 s | 1.946–2.212 s | 22.886 ms |
| То же, GPU 8 ms | 1.140 s | 1.106–1.194 s | 31.963 ms |
| То же, GPU 12 ms | 0.926 s | 0.899–0.951 s | 33.063 ms |

При первом подборе выбран default GPU budget **12 ms**: он сокращает медиану относительно 8 ms примерно на 19%,
при увеличении наибольшего измеренного кадра примерно на 1.1 ms. Относительно сборки до правок
полная готовность быстрее примерно в 9 раз. Создание объектов при 12 ms GPU budget завершается
за 0.847–0.900 s, медиана 0.880 s; оставшееся время занимают финализация текстур и fence.

После устранения гонки на завершении consumer и лишних запусков callbacks выполнено ещё три запуска
каждой сборки с выбранным default. Эти результаты относятся к окончательному коду:

| Финальное сравнение | Полная готовность, медиана | Диапазон полной готовности | Самый долгий кадр за 3 запуска |
|---|---:|---:|---:|
| Сохранённая сборка до правок | 8.367 s | 8.240–8.440 s | 38.903 ms |
| Финальная сборка, GPU 12 ms | 0.832 s | 0.827–0.891 s | 45.518 ms |

Полная готовность быстрее примерно в **10 раз**. Объекты готовы за 0.783–0.842 s,
медиана 0.784 s. Максимальный кадр в последнем сравнении вырос на 6.6 ms;
сохранение прежнего максимального frame time не заявляется. Выбранный бюджет отдаёт больше времени загрузке;
его можно уменьшить через `SetUploadBudget`. Данные первичного подбора показывают соответствующий обмен времени
полной загрузки на время кадра, но отдельные выбросы зависят также от ОС и драйвера.

Отдельная функциональная проверка окончательного кода: GPU completion 854.164 ms,
готовность объектов 798.644 ms, максимальный кадр 35.218 ms, 32 отрисованных кадра.
Этот запуск не входит в таблицы.

Разрешение harness значительно меньше обычного окна редактора. Эти цифры сравнивают загрузчики
при одинаковом рендере; они не гарантируют такой же frame time при другом разрешении, сцене,
на холодном диске или с большой отдельной моделью/текстурой. Бюджеты времени/байтов мягкие:
один ресурс/объект может превысить бюджет, разбиения его на части нет.

## Проверки

- CPU consumers обрабатывают всю небольшую очередь без единого вызова `PumpLoading()`.
- Результаты workers не публикуются непосредственно в resource maps.
- Byte backpressure учитывает неопубликованные results и pending textures/models, при заполнении останавливает
  производство и освобождает scheduler workers. GPU uploads возобновляют consumers и снимают pending-byte charge.
- GPU pump загружает больше четырёх маленьких текстур за кадр, когда позволяют байты и время.
- Plane/cube/sphere делят immutable CPU geometry и GPU buffers при независимых MeshID/materials.
  Кэш сфер различает tessellation и нормализует минимальные slices/stacks.
- Все 1000 кубов, включая куб стартовой сцены, используют один vertex buffer и один index buffer;
  каждый созданный куб рисуется в первом доступном кадре с плейсхолдером при незагруженном albedo.
- Отдельная контрольная сцена с готовыми MeshID и большим временным бюджетом подтверждает,
  что публикация может создать больше 32 объектов за кадр. Число объектов в 4 ms на stress-сцене не фиксируется:
  подготовка новых файловых запросов также требует времени.
- Проверены ошибки JSON/декодирования, material overrides, fence cleanup и shutdown при заполненном бюджете.
- D3D12 debug diagnostics без ERROR/CORRUPTION; native mixed scene / Play snapshot / physics regression проходят.

## Повторение

Сначала собрать текущий harness командой `tests/RunTextureTests.ps1`, затем выполнить
`tests/MeasureResourceLoading.ps1 -BaselineExecutable <preserved-debug-harness.exe>`.
Скрипт по умолчанию делает три запуска baseline и три запуска каждого бюджета 4/8/12 ms.
Для сравнения только выбранного default: `-UploadMilliseconds 12`.
`LSE_TEST_UPLOAD_MS` читается только тестом, не является настройкой приложения.

Первичный подбор сохранён в `tests/.build/loading-comparison/`.
Окончательное сравнение — в `tests/.build/loading-final-comparison/results.json`, `results.csv`
и `before-*.log` / `after-*-ms-*.log`. Директория задаётся параметром `-OutputDirectory`.
Baseline executable требуется сохранить до правок;
скрипт не меняет исходники, не откатывает рабочие файлы и не обращается к Git.
